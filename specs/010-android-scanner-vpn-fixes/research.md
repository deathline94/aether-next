**Date**: 2026-09-18

## 1. Discovered Gateways Mobile Layout & Character Column Distortion

### Problem Analysis
In `apps/android/src/App.css` (lines 2228–2274), `.discovered-row` was implemented with:
```css
.discovered-row {
  display: flex;
  align-items: center;
  justify-content: space-between;
  gap: 14px;
}
.discovered-info {
  display: flex;
  align-items: center;
  gap: 12px;
  min-width: 0;
  overflow-wrap: anywhere;
}
.discovered-actions {
  display: flex;
  align-items: center;
  gap: 10px;
  flex-shrink: 0;
}
```
On mobile devices in portrait orientation (viewport width ~360px–420px):
1. The `.discovered-actions` container (RTT latency badge + "Connect Direct" button) occupies ~195px and has `flex-shrink: 0`.
2. After accounting for parent padding (20px on each side) and row padding (16px on each side), available width for `.discovered-info` drops below 100px.
3. Inside `.discovered-info`, the tactile copy button (28px) and protocol badge (`MASQUE H3`, ~75px) leave under 10px of width for `<code>162.159.198.1:4500</code>`.
4. Because `.discovered-info` specifies `overflow-wrap: anywhere;` and lacks `white-space: nowrap;`, the layout engine breaks the IP address after every single character. The IP renders as a 17-line vertical stack of single characters, and the `.discovered-actions` cluster centers vertically against this tall column, colliding and overlapping with the text.

### Decision
- **Mobile Responsive Layout (`@media (max-width: 680px)`)**:
  - Restructure `.discovered-row` to stack vertically (`flex-direction: column; align-items: stretch; gap: 10px;`).
  - Top row (`.discovered-info`): stretches full width, aligns copy button, IP code, and protocol badge on a single unbroken line (`white-space: nowrap; font-size: 13px;`).
  - Bottom row (`.discovered-actions`): stretches full width, placing the latency badge on the left and expanding `.connect-direct-btn` (`flex: 1; height: 34px;`) across the remaining width.
- **Desktop Parity**:
  - Retain the horizontal single-row layout for viewports $> 680\text{px}$, but remove `overflow-wrap: anywhere;` in favor of `overflow: hidden; text-overflow: ellipsis;` to guarantee endpoints never break mid-character on any screen size.

### Alternatives Considered
- *Scale down font size to 8px on mobile*: Rejected because it harms readability and fails accessibility standards.
- *Truncate IP address*: Rejected because users need to see the full IP and port to know which endpoint was found and which port (e.g. 500, 4500, 8443) connected.

## 2. Fake IP Virtual Range vs Interface Address Collision (`mapdns`)

### Problem Analysis
In `apps/android/android/app/src/main/java/app/aethernext/AetherVpnService.kt`:
- `TUN_ADDR` is assigned `198.18.0.1/24`.
- `MAPPED_DNS` is assigned `198.18.0.2`.
- `writeHevConfig()` generates the `mapdns` configuration for `hev-socks5-tunnel`:
  ```yaml
  mapdns:
    address: 198.18.0.2
    port: 53
    network: 198.18.0.0
    netmask: 255.255.0.0
    cache-size: 10000
  ```
- `198.18.0.0/16` starts at `198.18.0.0` and sequentially maps queries to `198.18.0.1`, `198.18.0.2`, `198.18.0.3`, etc.
- When an app makes its first DNS lookup, `hev` allocates `198.18.0.1` (or `198.18.0.2`).
- When the application attempts to open a TCP or UDP socket to `198.18.0.1`, the Linux/Android kernel identifies `198.18.0.1` as the device's own local TUN interface address (local host route). The packets are routed to local loopback and never enter the TUN file descriptor for `hev-socks5-tunnel` to intercept and forward. The connection immediately drops.

### Decision
- Shift the `mapdns` virtual fake-IP pool to `198.19.0.0/16` (`network: 198.19.0.0`, `netmask: 255.255.0.0`).
- Both `198.18.0.0/16` and `198.19.0.0/16` fall within RFC 2544 benchmark space (`198.18.0.0/15`).
- The builder already declares `.addRoute("198.18.0.0", 15)`.
- `198.19.0.0/16` has 0 overlap with `198.18.0.1` (TUN interface IP) and `198.18.0.2` (DNS listener IP).
- Every fake IP generated by `mapdns` (`198.19.x.x`) routes cleanly into the TUN interface without collision.

### Alternatives Considered
- *Class E `240.0.0.0/4`*: Widely used by some desktop tun2socks tools, but some older Android kernels drop Class E addresses as non-routable / reserved. RFC 2544 `198.19.0.0/16` is guaranteed routable unicast across all Linux and Android kernels.

## 3. Android Private DNS (DoT) Validation & System Fallback Leaks

### Problem Analysis
On Android 9 through Android 15:
- The system includes "Private DNS" (DNS-over-TLS), which is set to "Automatic" by default.
- When `AetherVpnService` configures `builder.addDnsServer("198.18.0.2")`:
  1. Android's network management daemon (`netd`) attempts a DoT handshake on port 853 to `198.18.0.2:853`.
  2. `hev-socks5-tunnel`'s `mapdns` server only listens on port 53; it does not support TLS on port 853.
  3. The DoT validation probe fails or times out.
  4. Android marks the VPN network as having failed Private DNS validation.
  5. In accordance with Android resilience policies, `netd` silently falls back to the underlying physical network's DNS servers (cellular carrier DNS) or sends DNS queries directly over the physical network interface, bypassing the VPN tunnel.
  6. Furthermore, applications relying on DoT or modern async resolvers fail to resolve or route outside the tunnel.

### Decision
- In `AetherVpnService.kt`, configure both the local mapped resolver and upstream public resolvers via `VpnService.Builder`:
  ```kotlin
  builder.addDnsServer(MAPPED_DNS) // 198.18.0.2: port 53 fake-IP resolver
  builder.addDnsServer("1.1.1.1")   // Cloudflare primary DoT/DNS
  builder.addDnsServer("8.8.8.8")   // Google fallback DoT/DNS
  builder.addDnsServer("2606:4700:4700::1111") // Cloudflare IPv6 DNS
  ```
- All traffic to `1.1.1.1:853` and `8.8.8.8:853` is captured by the VPN default route (`0.0.0.0/0`) and forwarded via `hev-socks5-tunnel` through the local SOCKS5 proxy to Cloudflare/Google upstream.
- Port 853 TLS handshakes succeed over the tunnel! Android's Private DNS validation transitions to "Validated" (green).
- The system never triggers fallback to physical carrier DNS.

### Alternatives Considered
- *Instruct users to disable Private DNS in Android Settings*: Terrible user experience and violates requirements (users cannot be expected to reconfigure system network settings).
- *Implement a local DoT server in Kotlin*: Unnecessary overhead and complexity; routing DoT queries through the existing SOCKS5 tunnel resolves upstream DoT natively.

## 4. IPv6 Routing and Dual-Stack Tunnel Encapsulation

### Problem Analysis
On modern LTE and 5G cellular networks, carriers assign IPv6 addresses (or operate IPv6-only networks with 464XLAT).
- `AetherVpnService.kt` contained:
  ```kotlin
  .addAddress(TUN_ADDR_V6, 128)
  .addRoute("::", 0)
  ```
- But in `hev-socks5-tunnel.yml`, `tunnel:` had:
  ```yaml
  tunnel:
    mtu: 1280
    ipv4: 198.18.0.1
    icmp: 'drop'
  ```
- Notice that `ipv6:` was completely missing from `hev-socks5-tunnel.yml`.
- Any IPv6 packet sent by Android apps (or the CLAT translator) entered the TUN interface and was dropped by `hev` because lwIP had no IPv6 interface configured.
- Happy Eyeballs either stalled or traffic attempted to route over uncaptured network adapters.

### Decision
- Add `ipv6: '$TUN_ADDR_V6'` to `hev-socks5-tunnel.yml` under `tunnel:`.
- In `AetherVpnService.kt`, assign `addAddress(TUN_ADDR_V6, 64)` and route `::/0`.
- In `aether/src/socks.rs`, verify that SOCKS5 supports IPv6 (`ATYP_V6`) and UDP associate forwarding (already fully supported in the engine).
- Now, all IPv6 traffic is captured by `tun0`, ingested by `hev-socks5-tunnel`, and relayed through SOCKS5 without stalling or leaking.

## 5. Underlying Network Management

### Decision
- Keep `setUnderlyingNetworks(null)` to let the system automatically associate the VPN with the active default network (Wi-Fi or Cellular).
- Ensure `builder.addDisallowedApplication(packageName)` remains active so the engine process (`libaether.so`) can communicate with Cloudflare edge IPs over the physical network without creating routing loops.
